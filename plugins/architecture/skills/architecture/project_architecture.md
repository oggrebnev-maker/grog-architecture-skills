# Эталон устройства проекта

Эталон любого проекта владельца для работы с Claude Code. Читает агент, который пришёл в проект и ничего о нём не знает. Источник — репозиторий `oggrebnev-maker/grog-architecture-skills`, плагин `architecture`; версия — в `plugins/architecture/.claude-plugin/plugin.json`, изменения — `CHANGELOG.md` репозитория.

**Эталон — минимум, не потолок.** Проект может отличаться только в лучшую сторону: добавить нужное, назвать иначе, разложить подробнее. Каждое отличие — строка в `docs/DECISIONS.md` проекта: что иначе и почему лучше. Убирать обязательное и ослаблять правила нельзя.

**Как обновлять эталон.** Узнал важное для всех проектов — правка в клоне `grog-architecture-skills` (на сервере владельца — `/home/ya-business/grog-architecture-skills`), версия +1 в `plugin.json`, строка в `CHANGELOG.md`, тесты `bash test.sh`, коммит, push, сообщение владельцу «Записал в инфраструктуру: …». Проекты получают обновление командой `claude plugin update architecture@grog-architecture-skills`. Из другого проекта эталон не править.

---

## 1. Принципы

1. **Главный — Claude Code.** Все инструкции пишутся для него. Codex и другие агенты получают `AGENTS.md` — ссылку на `CLAUDE.md` и `.claude/rules/`.
2. **Сначала думать и искать готовое.** Есть подходящее — взять; близкое — доработать; нет совсем — писать своё.
3. **У каждого знания одно место.** Правило, факт, решение записаны один раз; остальные места ссылаются.
4. **Не дублировать код документами.** Что можно получить из кода — генерирует программа (раздел 13).
5. **Агентная система.** Повторяемую работу делает агент со своей инструкцией, входом и местом для результата; главный чат — оркестратор.
6. **Расширения переносимы.** Расширение (`add-ons/<имя>/`) устроено по этому эталону и забирается в другой проект целиком.
7. **Действующее отдельно от истории.** В рабочих файлах — только действующее; журналы, отчёты, evidence — в `docs/archive/`. Историю задним числом не переписывать.
8. **Знание живёт в репозитории.** Решения, правила, грабли — в файлах проекта. Память Claude локальна для сервера: туда только личное о владельце и ссылки.
9. **«Грабли» закрывать кодом.** Что можно проверить автоматически — хук, тест или `check.py`, а не строка в правилах.

## 2. Что агент решает сам, что спрашивает

| Сам | Спросить владельца |
|---|---|
| Структуру папок, имена, раскладку правил, перенос в архив | Что за продукт, для кого, главный сценарий — если нет в документах |
| Технические решения: библиотеки, код, тесты, ветки | Бизнес-правила: цены, тарифы, сроки, тексты для клиентов |
| Установку инструментов раздела 17 | Удаление чего-либо; платные сервисы, ключи, публикации, push в main, deploy |

- Необходимую работу — делать сразу. План показать **до** работы, только если шаг необратим, удаляет, затрагивает чужую незавершённую работу или требует бизнес-решения владельца; иначе план и итог — в отчёте.
- В сообщении — не больше одного вопроса, с вариантами и рекомендацией. Остальное, что ждёт решения, — списком «Ждёт решения» в отчёте.

## 3. Порядок действий

Проверка до и после — `python3 -B <папка навыка>/scripts/check.py <проект>`.

**А. Новый проект**
1. Нет git — `git init`. Инструменты установлены (раздел 17): иначе `bash install.sh` из `grog-architecture-skills`.
2. Спросить владельца о продукте (раздел 2), заполнить `context/product.md`.
3. Создать обязательное (раздел 4) из `templates/`: `.claude/settings.json` ← `project-settings.json`, `.gitignore` ← `gitignore.txt`, `scripts/env-names.sh`; `CLAUDE.md` по шаблону раздела 5.
4. `check.py` — FAIL 0. Отчёт владельцу.

**Б. Существующий проект**
1. `check.py` до; осмотреть `git status`, дерево, все `CLAUDE.md`/`AGENTS.md`/`README.md`, `.claude/`.
2. Перестраивать шагами, коммит на шаг, тесты проекта после шага; сломалось — откатить шаг. Ничего не удалять: старое — в `docs/archive/` (раздел 7). Папки с чужой незавершённой работой — после её завершения.
3. Перед записью в `CLAUDE.md` или `AGENTS.md` — `ls -la`: символьную ссылку сначала `rm`, потом писать обычный файл.
4. `check.py` после — FAIL 0; пункты раздела 18, которые скрипт не видит, — глазами. Отчёт: что смотреть, вывод `check.py` до/после, что не сделано и почему.

## 4. Структура

```
<проект>/
  CLAUDE.md                 [обязательно] вход по шаблону раздела 5
  AGENTS.md                 [обязательно] короткая ссылка на CLAUDE.md и .claude/rules/
  PROGRESS.md               [обязательно] где остановились, что дальше (раздел 7)
  README.md                 [по необходимости] для людей: что это и как запустить
  .gitignore                [обязательно] из templates/gitignore.txt
  .env.example              [если есть секреты] имена ключей без значений
  context/                  [обязательно] product.md, architecture.md, conventions.md, glossary.md
  docs/
    DECISIONS.md            [обязательно] решения владельца
    CHANGE_REQUESTS.md      [обязательно] новые идеи владельца
    REUSE_DECISIONS.md      [обязательно] что взято готовым
    superpowers/            [по необходимости] specs/, plans/
    manual/                 [если у продукта есть пользователи] реестр возможностей и справочник
    archive/                [по необходимости] история
  .claude/
    settings.json           [обязательно] запреты чтения, маркетплейсы, плагины (раздел 9)
    settings.local.json     [по необходимости] личное; в .gitignore
    rules/                  [обязательно в корне] правила проекта по темам
    agents/ skills/ commands/ hooks/ output-styles/   [по необходимости]
  prompts/                  [если продукт вызывает ИИ] промты продукта
  scripts/                  env-names.sh и служебные скрипты
  .github/workflows/        [по необходимости] CI (раздел 16)
  <код>/                    по стеку
  add-ons/<расширение>/     [по необходимости] та же структура (раздел 11)
```

Пустые папки «на будущее» не создавать. Файла `.claudeignore` в Claude Code нет — «что не читать» задаётся запретами `Read(...)` в `.claude/settings.json`.

## 5. CLAUDE.md

Грузится в каждом чате и переживает сжатие контекста: до 150 строк и 20 КБ. Каждый раздел — несколько строк и ссылка на подробности.

```markdown
# <Проект> — инструкции

## 1. Проект
<1–2 предложения: задача, пользователи, главный сценарий.>
Начало сессии: верх `PROGRESS.md`, `git status`; по задаче — файл из `context/`.

## 2. Агенты
<Таблица: агент — когда — что отдаёт. Порядок запуска — реестр агентной системы (ссылка).>

## 3. Инструменты
<Таблица плагинов и навыков проекта: что — откуда (маркетплейс) — что делает — когда применять.
Каждый плагин из enabledPlugins в .claude/settings.json — строкой здесь (check.py сверяет).
Команды, которые агент не угадает: сборка, тесты, запуск, журнал.>

## 4. Данные — источники истины
<Где материалы и куда писать результат. Каждый факт (цены, сроки, тарифы) — одно место и кто меняет.>

## 5. Стиль работы
<Только отличия этого проекта от общих правил владельца (~/.claude/CLAUDE.md). Нет отличий — «Общие правила владельца».
Стиль текстов для клиентов — не здесь, а в навыке агента-автора и prompts/.>

## 6. Порядок работы
<Что за чем, проверки перед «готово», ветки. Только после явного «да» владельца: …>

## 7. Грабли
<Что ломается, что выглядит правильным, но не работает. Лимиты сервисов — в CLAUDE.md того расширения или плагина.>

## 8. Решения
<Главные действующие решения строкой; все — docs/DECISIONS.md.>
```

**Писать:** команды, которые агент не угадает; отличия от общепринятого; как запускать тесты; ветки и коммиты; архитектурные решения этого проекта; особенности окружения; неочевидные грабли.
**Не писать:** видимое из кода; общеизвестное; подробную документацию API (ссылку); часто меняющееся; длинные объяснения; описание каждого файла; очевидное; отчёты и историю; повтор общих правил владельца.

**Как писать правила** (`CLAUDE.md`, `.claude/rules/`, агенты, навыки, промты):
- Действие + конкретика + проверяемое условие: «перед коммитом — `npm test`, 0 падений», а не «проверяй изменения».
- Запрет — с заменой: «Никогда X. Вместо этого Y.»
- Числа — для требований к результату («пост 600–900 символов»). Длину ответов агента числом не ограничивать — описать цель: «только то, что спросили».
- Без «старайся», «по возможности», «хорошо», «понятно», «качественно».
- Капс — не чаще раза на файл. Одно правило — в одном месте.
- Пути — полные от корня проекта.

**Импорты `@путь`** раскрываются целиком при старте и не экономят контекст; `.claude/rules/` не импортировать — они грузятся сами. **Личное** — `CLAUDE.local.md` (в `.gitignore`). **Правило, навык или агент:** правило — нужно в каждом чате или при работе с файлами по `paths:`; навык — для разовой задачи, грузится когда нужен; агент — задача, которую выгодно делать в отдельном контексте.

**AGENTS.md** — обычный файл, не символьная ссылка: «Главный файл инструкций — `CLAUDE.md` в этой папке; правила по темам — `.claude/rules/*.md`. Прочитать и выполнять.»

**Модуль-подключение** (плагин канала, библиотека для переноса) — свой жанр `CLAUDE.md`: пошаговое подключение и таблица ошибок; шаблон восьми разделов к нему не применять.

## 6. `context/`

Коротко и только действующее; длинные исследования — в `docs/archive/`, отсюда ссылка.

| Файл | Разделы |
|---|---|
| `product.md` | Для кого и какую задачу решает · Главные сценарии · Ценности и чего не обещаем · Модули и что работает (статусы, если ведутся в плане, — ссылкой) · Границы |
| `architecture.md` | Процессы и связи · Хранилища · Внешние интеграции · Путь действия: кнопка → права → задача → обработчик → результат · Карта действий (раздел 13) |
| `conventions.md` | Стек и версии · Структура кода · Тесты · Имена · Коммиты и ветки · Зависимости |
| `glossary.md` | Слова владельца и их значение |

## 7. Рабочие файлы и архив

| Файл | Правило |
|---|---|
| `PROGRESS.md` | Он же передача между сессиями. Новое — сверху: дата, задача, сделано, дальше, ждёт владельца. Больше 300 строк — старое в `docs/archive/progress/`. |
| `docs/DECISIONS.md` | Строка: дата, решение, причина, статус; отменённое — пометить, не удалять. Может называться иначе (например `OWNER_DECISIONS.md`), если путь указан в `CLAUDE.md`. |
| `docs/CHANGE_REQUESTS.md` | Строка: ID, дата, идея, зависимости, влияние, этап. Текущую задачу не бросать. |
| `docs/REUSE_DECISIONS.md` | Строка: дата, что искали, источник и лицензия, решение. Проверенное повторно не искать. |

**Архив.** `git mv` в `docs/archive/<тема>/`, связанные документы — вместе; текст не править; в папке — `README.md` с правилом пересчёта старых путей. Ссылки из действующих файлов — исправить в том же коммите.

## 8. `.claude/`

- **`rules/`** — файл на тему: `workflow.md`, `reuse.md`, `git.md`, `security.md`, `design.md`. Только то, что относится к проекту. Узкое — с `paths:`:
  ```markdown
  ---
  paths: ["<папка>/**"]
  ---
  <Правило для этой папки.>
  ```
- **`agents/`** — проектные агенты (шапка: `name`, `description` — когда вызывать, `model`, `tools`, `skills`). Общие `reuse-scout` и `manual-keeper` приходят с плагином `architecture`; проектный файл с тем же `name` перекрывает общий. Агенты видны, когда чат открыт в этой папке или ниже.
- **`skills/<имя>/SKILL.md`** — навыки проекта; вложенные `<папка>/.claude/skills/` подключаются при работе в папке.
- **`commands/`**, **`output-styles/`** — по необходимости.
- **`hooks/`** — скрипты автодействий проекта; хук объявляется в `settings.json`, путь — `"$CLAUDE_PROJECT_DIR"/.claude/hooks/<скрипт>`.
- **`settings.json`** — в git; не наследуется от родительских папок: у корня и у каждого расширения свой. **`settings.local.json`** — личное, в `.gitignore`.

## 9. Инструменты проекта — что подгружается вместе с проектом

1. `.claude/settings.json` проекта объявляет маркетплейсы (`extraKnownMarketplaces`) и включённые плагины (`enabledPlugins`); образец — `templates/project-settings.json`. Обязателен `architecture@grog-architecture-skills`.
2. Открыв проект и подтвердив доверие к папке, Claude Code регистрирует маркетплейсы и сообщает о не установленных плагинах; установка — `claude plugin install <плагин>@<маркетплейс>` или `bash install.sh`.
3. Раздел 3 `CLAUDE.md` — таблица этих плагинов: откуда, что делает, когда применять. `check.py` сверяет её с `enabledPlugins` и проверяет, что маркетплейс каждого плагина объявлен.
4. Плагин, который нужен не каждому проекту, ставится выключенным (`defaultEnabled: false`) и включается строкой в `enabledPlugins` проекта. Навыки владельца (`owner-skills`) грузятся по описанию только когда нужны — их включать везде.
5. Навыки проекта, не оформленные плагином, — `.claude/skills/` проекта; общие навыки владельца ставит `install.sh` (раздел 17).

## 10. `prompts/`

Промты, которые вызывает продукт, — файлами по назначению (`<назначение>.md`), не строками в коде. Стиль и запреты текстов для клиентов — здесь и в навыке агента-автора.

## 11. Расширения

- Расширение — то, что забирается в другой проект целиком: свои `CLAUDE.md`, `AGENTS.md`, `context/`, `PROGRESS.md`, рабочие файлы, `.claude/settings.json`, код, тесты; без зависимостей от ядра.
- Вложенные расширения — в `add-ons/` расширения; `check.py` проверяет их рекурсивно.
- Расширение или агент: переносится отдельно — расширение; шаг работы внутри — агент.
- Работа над расширением — чат открывается в его папке: видны его агенты, навыки, `settings.json`; `CLAUDE.md` корня грузится сам, его правила не повторять.

## 12. Агентная система

Реестр: `| № | Шаг | Агент | Навык | После кого | Результат (куда) | Статус |`.

- В зарегистрированной системе шаг делает его агент; пока агент разрабатывается — статус шага «разрабатывается», работа шага ждёт агента.
- Агент работает со своими входами и пишет только в свою папку результата. Агентам нельзя: публиковать, тратить деньги, писать людям, читать секреты, push и слияние в main.
- Задание агенту: цель одной фразой; его файлы и чужие; что вернуть; как понять, что готово. Агенты, пишущие код, — каждый в своём git worktree; сливает оркестратор после тестов и ревью.
- Звать: независимые задачи параллельно, широкий поиск, свежий взгляд. Не звать: задача на минуты, зависимые шаги, нужен весь разговор с владельцем. Перед раздачей больше 5 агентов — сказать владельцу, сколько и во что обойдётся.
- Модели: поиск без оценки — Haiku; поиск с оценкой и исполнители — Sonnet; архитектура, ревью, трудное — Opus.
- Агенты Claude Code — кухня разработки. Действие пользователя в продукте выполняет код сервера: кнопка → права → задача в очереди → обработчик → промт → результат.

## 13. Карта действий сервера

Если есть API: штатный генератор OpenAPI стека пишет файл карты, тест сверяет его с кодом; изменил маршруты — перегенерировать и коммитить вместе с кодом. Fastify — `@fastify/swagger` (MIT), регистрировать до маршрутов; публичную страницу без решения владельца не открывать.

## 14. Порядок работы и ветки

- **Процесс.** Новая возможность или изменение поведения, видимое пользователю, — Superpowers целиком: brainstorming → спецификация → план → TDD → проверка перед «готово». Исправление ошибки или правка без изменения поведения — падающий тест → правка → тесты. Документы и инструкции — без тестов, с проверкой `check.py`.
- **Готовое прежде своего:** перед новым модулем, интеграцией, агентом, навыком, промтом — агент `reuse-scout`. Лицензии MIT, Apache 2.0, BSD, ISC — можно; GPL/AGPL и запреты коммерческого использования — с согласия владельца. Версии зависимостей — точные (`--save-exact`), выпущенные 14 и более дней назад.
- **Внешние сайты** — Firecrawl CLI. Сверяться с официальной документацией — при новой зависимости, интеграции, утверждении о внешнем инструменте или API.
- **Интерфейсы** — Claude Design; реализация только после «утверждаю» владельца именно полученного результата.
- **Ветки.** `main` — рабочая версия продукта. Работа — в ветке задачи или расширения; push своей ветки — сам. Слияние в `main` — после тестов, `check.py` и «да» владельца.
- **Коммиты** — только свои пути: `git commit -m "…" -- <пути>`. Чужие незакоммиченные правки в нужном файле — коммит через временный индекс (`GIT_INDEX_FILE`), затем `git reset -- <пути>`.
- **Инструмент не работает** — точная ошибка в `PROGRESS.md`, продолжать независимую работу; ограничения среды не обходить.

## 15. Секреты

- Значения — только в `.env*` (в `.gitignore` по `templates/gitignore.txt`); имена ключей — в `.env.example` (в git). Никогда не печатать значения; имена — `bash scripts/env-names.sh <файл>` (копия `templates/env-names.sh`).
- Хук `guard-env` (плагин `architecture`) блокирует команды со строкой `.env`, `.env.*`, `.envrc`, кроме `.env.example` и вызова `env-names.sh`; без `jq` блокирует всё. Хук — страховка по тексту команды, не песочница: что откроет запущенная программа, он не видит.
- `install.sh` добавляет запреты `Read`/`Edit` для `.env`, `.env.*`, `.envrc` в `~/.claude/settings.json`.

## 16. CI — по необходимости

`.github/workflows/check.yml`: на каждый push — тесты проекта и `python3 -B check.py . --no-user` (скрипт — из клона `grog-architecture-skills` нужной версии). Добавлять, когда в проекте работают больше одного человека или чата.

## 17. Инструменты и установка

Список всего, что ставится на сервер, — `manifest.json` в папке этого навыка: маркетплейсы, плагины, навыки, npm-программы, скрипты настройки, известные дубли; у каждой строки — зачем. Установка и приведение в соответствие — `bash install.sh` из клона `grog-architecture-skills` (повторяемо: ставит недостающее, обновляет, лишнее только называет). `check.py` проверяет, что все плагины списка включены.

Добавить сторонний инструмент для всех серверов — строка в `manifest.json` (с «зачем»), версия эталона +1, `CHANGELOG.md`, push, `bash install.sh`. Свой навык — папка `skills/<имя>/` репозитория (плагин `owner-skills`).

Вручную после скрипта: `firecrawl login`; если `~/.claude/CLAUDE.md` отличался — сравнить с `~/.claude/CLAUDE.md.grog-new`; перезапустить Claude Code. Внешний сервис: Claude Design (claude.ai) — экраны.

Ревью и стражи: встроенные `/code-review` и `/security-review`; агенты `pr-review-toolkit` — после каждой задачи с кодом; `security-guidance` — проверка при правках и перед коммитом; `typescript-lsp` — ошибки типов; `hookify` — повторно нарушаемое правило превратить в хук; `guard-env` — секреты.

## 18. Проверка соответствия

`check.py` проверяет: `CLAUDE.md` (обычный файл, 8 разделов по порядку, размер, нет `@`-импорта правил), `AGENTS.md`, `context/`, git, `PROGRESS.md` и длину журналов, рабочие файлы, `.claude/rules/`, запреты чтения, плагины и маркетплейсы, таблицу инструментов, `.claudeignore`, `.gitignore` для секретов и личных файлов, формулировки, ссылки на файлы; расширения — рекурсивно; уровень пользователя — общие правила, плагин, `jq`, Firecrawl.

Агент проверяет сам: содержание `context/` по разделу 6; правила по «Как писать правила»; нет повторов общих правил владельца; реестр агентов с колонкой «после кого»; карта действий (если есть API); промты в `prompts/` (если продукт вызывает ИИ); история — в архиве.
